# Telemetry Monitor Deployment

The monitor runs as a Flask application from `monitoring/`. It subscribes to the configured MQTT topic on the server, persists a bounded message history in SQLite, and serves the dashboard only to authenticated sessions. The browser never connects to the MQTT broker and never receives broker credentials.

## Configure

From the repository root in PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Edit `.env` and set a unique `APP_SECRET_KEY`, an operator `APP_USERNAME`, and your MQTT host, username, and password. Generate a signing key with:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Replace `APP_PASSWORD_HASH` with a hash generated by the application:

```powershell
python -m monitoring.password_hash
```

The command prompts for the password twice and requires at least 14 characters. Paste its output into `.env`; do not store a plaintext monitor password there. Keep `.env` private. MQTT uses TLS on port 8883 by default.

## Run Locally

For a local preview, set `APP_ENV=development` in `.env`, then run:

```powershell
flask --app monitoring:create_app run --host 127.0.0.1 --port 5000
```

Open `http://127.0.0.1:5000`. Development mode does not set secure-cookie or HSTS flags, so do not use it for a client-facing deployment.

## Run on Ubuntu

Copy the updated project to the Ubuntu machine (a fresh Git clone will not include local, uncommitted changes), then from the repository root:

```bash
sudo apt update
sudo apt install -y python3-venv python3-pip
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
python -c 'import secrets; print(secrets.token_urlsafe(48))'
python -m monitoring.password_hash
```

Edit `.env`: set `APP_ENV=development` and `RATELIMIT_STORAGE_URI=memory://` for a short trusted-LAN preview, paste the generated signing key into `APP_SECRET_KEY`, set `APP_USERNAME` and the hash from `monitoring.password_hash`, and fill in the MQTT host and credentials. Keep `.env` private.

Start Waitress on the Ubuntu machine's LAN interface:

```bash
waitress-serve --host=0.0.0.0 --port=5000 --threads=8 --call monitoring:create_app
```

Find its LAN address with `hostname -I`, then open `http://<ubuntu-ip>:5000` from the other device on the same Wi-Fi. If UFW is enabled, allow port 5000 only from your trusted LAN subnet, for example `sudo ufw allow from 192.168.1.0/24 to any port 5000 proto tcp` (replace the subnet to match your network).

This HTTP setup is only for a temporary trusted-LAN preview; credentials and session cookies are not encrypted in transit. For a client-facing deployment, use a domain or trusted local certificate with an HTTPS reverse proxy, set `APP_ENV=production`, bind Waitress to `127.0.0.1`, enable Redis-backed rate limiting, and enable `TRUST_PROXY=true` only behind a correctly configured proxy. Do not forward port 5000 from the internet.

## Production

Set `APP_ENV=production`, use a strong private signing key and password hash, and set `RATELIMIT_STORAGE_URI` to a Redis instance shared by the application. The in-memory limiter default is suitable only for local development. Keep the Redis service private.

Run one Waitress process so there is exactly one MQTT ingestion client writing to SQLite:

```powershell
waitress-serve --host 127.0.0.1 --port 5000 --threads 8 --call monitoring:create_app
```

Place a trusted HTTPS reverse proxy in front of Waitress for the client demo. Keep Waitress bound to loopback and enable `TRUST_PROXY=true` only when the proxy overwrites forwarded headers. The application sets secure session cookies in production, enforces CSRF tokens, rate-limits login/API traffic, applies browser security headers, and exposes an unauthenticated `/healthz` liveness endpoint. Back up `TELEMETRY_DB_PATH`; history is capped by `TELEMETRY_MAX_ROWS`.

The current firmware source contains MQTT credentials. Rotate broker credentials before a client demonstration, then configure the new credentials only in the server's `.env` and firmware's private device configuration.
